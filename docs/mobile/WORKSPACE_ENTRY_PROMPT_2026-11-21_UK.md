# Робочий промт · KNABA DE · мобільний вхід після авторизації

Продовж розробку існуючого KNABA DE у `ziko1/knaba`. Виконай етап 1 із плану. Підготуй перевірювану зміну в чинному Draft PR #143 для відкритої задачі #142. Результат має бути помітний після входу у звичайний мобільний застосунок. Для наступного інкременту передай докази й першу незакриту залежність.

1. **Віднови контекст.** Прочитай кореневий та ERP AGENTS.md, V4 target, актуальні project memory, roadmap, backlog і протоколи Android/iOS. Прочитай батьківський мобільний master prompt. Перевір PR, head/base SHA, статус GitHub Actions та зміни, яких ще немає в описі PR. Працюй у чистому checkout. Якщо HEAD перейшов уперед, спочатку зістав уже внесені зміни.
2. **Відтвори проблему.** Простеж шлях від ERP-входу або відновлення до першого екрана та першого запиту робочих даних. Пройди обидві платформи. Підготуй синтетичні приклади користувача з однією роллю, кількома дозволеними кабінетами, невідомою роллю з широкими дозволами, відомою роллю без відповідних прав та канонічного спеціаліста. Для відтворення використай наявну тестову транспортну реалізацію і перевір видимий стан та лічильник викликів.
3. **Зістав контракт.** Виведи доступні кабінети з актуального ERP actor, його ролей та прав, зістав із реєстром на сервері. Для одного доступного кабінету відкрий його автоматично, для кількох покажи доступний із клавіатури/скрінрідера вибір, для порожнього набору поясни стан та залиш вихід. Явно визначені внутрішні спеціалісти мають зберегти доступ до вже дозволених робочих операцій. Перевір обидва різновиди Bauleiter. Перевірку живого партнера віднеси до серверного контракту з підтвердженою ідентичністю.
4. **Внеси мінімальну зміну.** Використай чинну модель сесії, UI, каталог модулів і механізм відновлення. До вибору дозволяй лише дії зі входом, сесією й відновленням у межах наявної авторизації. Не завантажуй огляд, списки або команди робочого кабінету. Після вибору застосовуй поточні серверні права й фільтр обраного кабінету. При зміні кабінету чи завершенні сесії прибирай попередню навігацію і застарілі відповіді. Сервер вирішує питання company/site/customer scope і кожної команди.
5. **Збережи сумісність.** Перевір обраний кабінет на клієнті, працівникові, керівникові та власникові, а також штатні тести на склад, бухгалтерію, вузькі дозволи й відновлення незавершеної команди. Назви кабінетів та повідомлення перевір у DE, EN, PL, LT, RU, UK. Збережи наявну поведінку MFA, logout і локального журналу. Зайві залежності, переписування API та зміни production виходять за межі етапу.
6. **Перевір конкретну ревізію.** Запусти цільові Android JUnit/Robolectric та iOS XCTest у доступному середовищі, перевір локалізації. На чистому commit виконай `npm run audit:source`, `npm run verify:modules`, `npm test` з Node 24 та перевір автоматичний CI. Рецензент незалежно зіставляє рольові предикати, показ екранів, запити до вибору та збереження легітимного доступу. Виправ знайдені дефекти й повтори відповідні перевірки. Старі логи прив’язуй тільки до їхньої ревізії.
7. **Передай результат.** Вкажи PR, точний SHA, виконані команди, PASS/FAIL/BLOCKED/NOT_RUN із причиною, посилання на CI та хеші фактично перевірених артефактів. Відокрем синтетичні transport-тести від справжнього API/PG, симулятор від фізичного пристрою. Наступна задача має називати конкретний екран, акаунт, операцію й критерій успіху. Залиш PR у draft. Міграції, публікація застосунків і виробничі зміни потребують окремого погодження.
