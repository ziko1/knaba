# KNABA DE — мобільний кандидат 0.5.0 / build 6

Це продовження чинного проєкту KNABA DE. Повна специфікація, 72 критерії V4 і збережені вимоги V3 залишаються обсягом приймання. Цей інкремент закриває конкретні прогалини в нативних застосунках; загальний статус продукту залишається **NOT_READY**, доки не завершені спільна ідентичність, усі спеціалізовані сценарії та зовнішні приймання.

## Що змінилося

| Частина | Поведінка кандидата |
|---|---|
| Обидві платформи | 39 розділів ERP, видимих за фактичними дозволами; склад, закупівлі, пропозиції клієнтів, табелі, поїздки, розрахунки, виплати, звіти та звернення. Назва ролі не надає додаткового доступу. |
| Android | Дії з картки 15 типів записів. ID і очікувана версія беруться з відкритого запису; версія пропозиції та особиста ідентичність працівника в призначенні не вигадуються. Каталог дій має пошук. |
| iOS | Зашифрований журнал незавершеної команди, записаний перед POST. Після невідомого результату повторюються ті самі bytes/key/version; повтор лише явний після свіжого входу та `/me` того самого користувача, компанії й сервера. |
| Сеанси iOS | Вихід очищає локальні повноваження до очікування мережі. Пізні відповіді не відновлюють стару сесію; сторінки одного запиту не змішують різні identity. |
| Мови та бренд | DE/EN/PL/LT/RU/UK; чинний знак із трьома будівлями. Android adaptive/themed launcher icon; iOS opaque AppIcon 1024×1024. Джерело й hashes — `BRAND_ASSETS.json`. |
| Пакування | Android APK/AAB з перевіркою підписів, однакового сертифіката й цілісності. iOS owner archive перевіряє фактично експортований застосунок. Версія береться з Gradle/XcodeGen; фінальна квитанція не переживає невдалу нову спробу. |

Сервер залишається джерелом істини для company/site/customer/self scope, MFA, дозволів і переходів стану. Видимість меню та загальна форма команди не замінюють приймання повного робочого процесу. Файли в нативному розділі поки не означають завершений capture/upload/preview workflow для всіх форматів.

## Android: перевірка кандидата

Тестовий пакет — `de.knaba.mobile.test`, назва **KNABA Test**, versionCode **6**. Він відокремлений від `de.knaba.mobile`. APK придатний для тестового встановлення; AAB є пакетом для подальшої процедури розповсюдження й не встановлюється як APK. Debug-підпис не є підписом власника для виробничого релізу. Сертифікат кожної конкретної збірки перевіряється за її receipt; hosted CI використовує власний debug key і не гарантує оновлення попереднього локального APK.

1. Звірити SHA-256 APK з квитанцією саме цієї збірки.
2. Встановити APK на дозволений тестовий Android 12+; зафіксувати модель, ОС, package/version і результат запуску.
3. На екрані входу вибрати потрібну мову. Режим «Тест без сервера» використовує явно вигадані task/chat дані й не є перевіркою ERP.
4. Для справжніх даних увійти в дозволений тестовий ERP через його HTTPS origin. Вхід на сайті та ERP поки окремі.
5. Перевірити дозволені та заборонені розділи для клієнта, працівника, внутрішнього Bauleiter, складу, закупівель і бухгалтера. Перевірити іншу компанію/об’єкт/клієнта та відкликання доступу через реальний сервер.
6. Для запису перевірити відкриту версію, доступні дії, відмову після конфлікту версії та збереження первинного запиту після втрати ACK. Не підміняти невизначений запит новим ключем.

Пакування після встановлення зафіксованих JDK17 / Gradle8.13 / SDK36:

```bash
cd erp/apps/mobile-android
# KNABA_JSON_TEST_JAR: org.json 20240303, перевірений pinned hash у test-transport.sh.
bash scripts/package.sh prototype
```

Результати з’являються в `build/distribution/prototype/` лише після проходження перевірок. `receipt.json` містить package/version, signer fingerprint, hashes APK/AAB та source inputs. `release` потребує чинного keystore власника і відповідних змінних `KNABA_ANDROID_*`; паролі не передаються в аргументах команд чи звітах. Ця робота не створює новий виробничий ключ.

## iOS: Simulator, джерела і підписаний застосунок

Перший рівень перевірки — кореневий `.github/workflows/native.yml`: конкретний Xcode/SDK, справжній завантажений Simulator і `xcodebuild test` з `.xcresult`. Успішний Simulator не підтверджує встановлення на iPhone, поведінку Keychain після reboot або фоновий GPS на пристрої.

Для локальної перевірки на Mac:

```bash
cd erp/apps/mobile-ios
bash scripts/build.sh
```

Portable source archive має тип `XCODE_SOURCE_ONLY_NOT_IPA`. Перед використанням звірити SHA-256 архіву з handoff-квитанцією. Всередині `IOS_SOURCE_MANIFEST.json` містить точні hashes файлів. Owner archive приймає незмінений portable manifest; його Git SHA явно позначається як заявлений у manifest. Звичайний Git checkout перевіряє власний HEAD до й після збірки.

Підписаний IPA створює `bash scripts/archive-release.sh` на Mac з Apple team власника, чинним профілем і перевіреним ExportOptions.plist. Скрипт перевіряє підпис експортованого Payload, Team ID, App ID prefix, bundle ID і строк профілю. App ID prefix перевіряється окремо від Team ID. Фактичне виконання owner signing потребує цих ресурсів; джерельна перевірка скрипта не є підписаним IPA.

## Що вже перевірено локально

На зафіксованому наборі вихідних файлів виконані clean Android assemble/bundle/lint та **32 Robolectric tests**: 27 інтерфейсу і 5 storage, без failures/skips. Lint: 0 errors, 17 warnings. Окремо: 74 transport/journal assertions, 38 demo checks, 39 locale/clock/auth assertions, 30 синтетичних geometry assertions; 62 перевірки сумісності contextual actions з executable ERP schema; TypeScript і 28 кореневих тестів. Перевірка AAB прийняла оригінал і відхилила неправильний signer, змінений DEX, непідписаний додатковий файл та відсутній manifest.

Robolectric, HTTP doubles та test key provider мають явні межі. Вони не доводять живий PostgreSQL commit після втрати відповіді, апаратний Keystore/Keychain, реальний GPS або компанійне UAT. Остаточний Git SHA, hashes артефактів і результати hosted CI потрібно брати з фактичної квитанції кандидата, не з попередніх історичних логів.

## Незакриті критерії повного завершення

- F1–F4 спільного site/ERP binding, link/unlink, обміну сесіями та відкликання; email не створює автоматичну прив’язку.
- Спеціалізовані мобільні форми, повні client/worker/partner/operator lifecycle journeys, медіа, provider/push і решта вимог канонічного backlog.
- Підписи власника, актуальні store вимоги, фізичні Android/iPhone install/upgrade/data retention, мінімальна й поточна ОС.
- Дозволене тестове середовище, дані/облікові записи та owner UAT; чинні зовнішні політики й провайдерні налаштування.
- Restore/migration/load та остаточне приймання exact artifact/config.

Перед downgrade невизначені команди потрібно звірити з ERP. Видалення застосунку чи журналу не скасовує серверний ефект. Нові зміни не виконують merge, production deploy, публікацію в магазинах або активацію платних сервісів.
