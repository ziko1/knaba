# KNABA Android 0.4.3 — автоматичне підключення та дані

## Мета і поточна межа

Запит користувача: дані мають автоматично підтягуватись із сервера; у звичайному вході не потрібно вводити адресу ERP. Завдання `MOBILE-013` продовжує наявний Android-застосунок KNABA DE. Версія 0.4.3 / versionCode 7 зберігає `de.knaba.mobile.test`, попередню тестову підписувальну ідентичність та іконку компанії.

**Живе підключення поки заблоковане конфігурацією сервера.** 08.11.2026 о 08:00 UTC публічний GET `https://knaba.de/api/public/release` з ідентифікатором клієнта `KNABA-Android-Discovery/1` повернув HTTP 200, JSON schemaVersion 1, stage `prototype`, **`erpOrigin: null`**. Це доводить доступність публічної конфігурації, але не готовність ERP. Два попередні запити зі стандартним клієнтом Python отримали 403; причина фільтрації на сервері не доведена. Точні спостереження й хеш успішної відповіді: [public-server-probe.json](evidence/android-autosync-20261108/public-server-probe.json).

Адресу чинної ERP не вигадано. Приватного доступу до серверного runtime у цьому сеансі не підтверджено. Налаштування змінних середовища, перезапуск production, міграція облікових записів і перевірка на телефоні залишаються окремими воротами.

## Реалізована поведінка

1. Застосунок сам запитує фіксований офіційний endpoint. Ручне поле адреси та збережений колись `erp-origin` не визначають місце надсилання пароля.
2. Дозволено тільки чистий HTTPS origin на `knaba.de` або його піддомені, порт 443, без userinfo, шляху, query чи fragment. Зовнішній хост потребуватиме окремого погодженого перегляду політики. Redirect, HTML/сторінка входу, інша схема JSON, завелика відповідь і відсутня конфігурація не приймаються як готова ERP.
3. Перед входом додатково перевіряється наявний серверний `/ready`: JSON `ready: true`, `database: "CONNECTED"`. Цей запит не передає пароль, cookie або токен. Це перевірка залежностей, а не доказ доступу користувача до компанії.
4. Коли сервер готовий, користувач входить у підтверджений ERP-акаунт. Наявна серверна авторизація, 2FA, CSRF, прив’язка user/company та журнал невизначених команд зберігаються. Спільний вхід сайт↔ERP цим завданням не створюється.
5. Після входу автоматично завантажується головний екран. Списки, картки записів, канали й каталог дозволених дій оновлюються кожні 30 секунд видимості; відкрита розмова — кожні 15 секунд. Повернення до застосунку викликає нове читання, якщо серверний Retry-After ще не обмежує запити.
6. Пошук, кількість відкритих записів, позиція прокрутки та чернетка повідомлення не обнуляються під час оновлення. Кнопка «Оновити» використовує той самий шлях без перебудови всього екрана. Картка отримує свіжу версію перед відкриттям форми дії; сервер надалі перевіряє expected_version.
7. Нова синхронізація не запускається у прихованому Activity. Уже розпочатий обмежений запит може завершитися. Один виконавець серіалізує ERP-запити; пізня відповідь зі старого екрана не змінює новий.
8. При мережевій помилці останні дані залишаються видимими з позначкою часу й попередженням про застарілість. Повторні GET мають експоненційну затримку з випадковим додатком; локальна межа — 120 секунд. Валідний Retry-After для 429/503 має пріоритет і може збільшити затримку. Автоматичних повторів змін даних немає.
9. Перед оновленням перевіряється `/me`. Втрата сесії, 403 під час читання, зміна user/company/roles/permissions/site/customer/warehouse scope прибирають приватний екран і вимагають повторного входу. Недоступна картка також не залишається як нібито чинний запис.
10. Форми команд не оновлюються самі. Невизначене надсилання зберігає текст і початковий idempotency key; повтор можливий тільки явно. Демо доступне окремою другорядною кнопкою тестового APK, не вмикається при відмові сервера. GPS не запускається цим механізмом.

Публічна конфігурація повторно перевіряється кожні 60 секунд видимості, доки не налаштована; мережеві відмови використовують backoff. Пароль і ERP-сесія робочого простору не зберігаються між завершеннями процесу. Дані екранів кешуються лише в пам’яті; це не офлайн-репліка ERP і не фонові push-сповіщення. Окрема прив’язка пристрою для робочого часу/GPS лишається чинним окремим потоком.

## Що потрібно налаштувати на сервері

Спочатку потрібен підтверджений чинний ERP origin, його PostgreSQL і реальна компанія/ERP-акаунт. Факт роботи корпоративного сайту або облікового запису сайту не доводить наявність цих компонентів. У `deploy/knaba-modules.json` ERP позначено як `source-only`; це опис вихідного коду, а не повна інвентаризація живого VPS.

Наявний `corporate-site/vps/public-release.mjs` уже читає **`KNABA_ERP_PUBLIC_ORIGIN`** з середовища процесу сайту і повертає `erpOrigin`. Новий endpoint або передавання секретів у конфігурації не потрібні.

Для задокументованої Docker Compose інсталяції змінна належить `/srv/knaba/vps/config/site.env`, який підключений через `env_file` у `corporate-site/vps/docker-compose.yml`. Це не той самий файл, що `/srv/knaba/vps/.env` для Compose interpolation. Фактичний активний сервіс та шлях необхідно звірити перед зміною. Додати тільки одну непорожню змінну з реально перевіреним HTTPS origin; не підставляти приклад або адресу сайту замість ERP.

Після погодженої зміни runtime-конфігурації й контрольованого перезапуску перевірити:

| Запит / сценарій | Потрібний доказ |
| --- | --- |
| `GET https://knaba.de/api/public/release` | HTTP 200 JSON, schemaVersion 1, точний ненульовий `erpOrigin` |
| `GET <підтверджений ERP origin>/ready` | Прямий HTTP 200 JSON, `ready: true`, `database: "CONNECTED"`, без redirect або Access login |
| `GET <ERP origin>/api/v1/me` без облікових даних | Відмова в приватному доступі; жодних записів компанії |
| Вхід погодженим користувачем у APK | Правильні user/company/roles, актуальні дані PostgreSQL |
| Зміна тестового запису на сервері | Новий стан з’являється на телефоні без ручного оновлення; чернетка чату збережена |
| Втрата/відновлення зв’язку, згортання/повернення | Чесна застарілість, автоматичне відновлення, відсутність повторної зміни даних |
| Відкликання прав / вихід / інший користувач | Приватні записи не переходять між сесіями |

Не включати cookie, пароль, OAuth secret, company PII або загальнодоступний обхід автентифікації до release JSON. Для серверного релізу врахувати актуальні auth-виправлення PR123 HEAD `9ff77d7b0161a4dde84314f2df327e4594e0eb0c`, звірені read-only в цьому сеансі; Android-файли там не змінені від наявної бази. Цей мобільний checkpoint не є прийманням старої серверної гілки для deployment.

## Перевірки та відкриті ворота

Локальні перевірки використовують скомпільований Android-код у Robolectric і явні синтетичні HTTP fixtures. Вони покривають конфігурацію, readiness, редиректи, межу відповіді, недовірені хости, таймаути, Retry-After, lifecycle, search/draft, пізні відповіді, зміну scope та невизначені записи. Фізичний телефон, справжній ERP-акаунт і end-to-end серверні дані ними не підміняються. Точні результати збірки й хеш APK записуються в `evidence/android-autosync-20261108/verification.json` після завершення фактичного запуску.

Незалежне рев’ю **NOT_RUN**: виклики агентів `server_config_review` і `foreground_sync_review` завершилися помилкою місткості контексту до виконання роботи. Повторна перевірка автором не названа незалежною. Витратні зовнішні AI-провайдери не активувалися.

Попередня автоматична перевірка дозволів відхилила GitHub push цієї гілки через відсутність явного дозволу на публікацію коду. Інший спосіб публікації не використано. Правила користувача та root `AGENTS.md` також вимагають конкретного підтвердження production/DNS/merge; такі зміни не виконувалися. Наступні зовнішні кроки: підтвердити ERP origin/runtime та дозволену серверну конфігурацію, незалежно переглянути candidate, виконати телефонний UAT.

## Встановлення і відкат

APK 0.4.3-test призначений для оновлення тієї самої `KNABA Test` зі збереженим сертифікатом. Передавати оригінальний standalone APK; не перейменовувати ZIP і не видаляти попередній застосунок або його дані як спосіб обійти помилку встановлення. Реальне оновлення й збереження даних на телефоні ще потребують перевірки.

Мобільна зміна не мігрує базу або encrypted journal. Код можна повернути до попереднього checkpoint, однак стандартний Android installer не гарантує downgrade versionCode 7 → 6: для відкату на телефоні підготувати той самий попередній код з вищим versionCode і тим самим ключем. Якщо майбутня зміна серверного origin виявиться хибною, оператор відновлює попереднє перевірене значення змінної та runtime-конфігурацію; автовизначення не переносить чинні cookie між серверами.
