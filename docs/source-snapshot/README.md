## Приватні параметри операторських скриптів

Публічні копії п’яти скриптів отримують прив’язані до сервера значення з локальних налаштувань. Гілка містить вихідний код і тести. Для перенесення на інший стенд власник налаштовує відповідні значення у своєму середовищі.

| Скрипт | Локальне налаштування |
| --- | --- |
| `ops/lead-agent/backup-lead-agent.py` | Файл `/srv/knaba/lead-agent/private/backup-qa-uuids.json` з двома різними UUID тестових клієнтів. |
| `ops/lead-agent/connect-knaba-whatsapp.py` | Очікуваний ID номера Meta з `KNABA_META_EXPECTED_PHONE_NUMBER_ID` у приватній конфігурації оператора. |
| `ops/lead-agent/lead-agent-publish.py` | Дозволені Cloudflare account ID та zone ID у приватному `publish-cloudflare-scope.json`. |
| `ops/customer/knaba-domain-setup.sh` | Account ID, zone ID та tunnel ID **захищеної інфраструктури розробника** у `excluded-developer-scope.json`. Скрипт виключає їх із допустимих цілей. |
| `ops/maintenance/knaba-r2-setup.sh` | Назва приватного R2 bucket у змінній `KNABA_R2_BUCKET`. |

## Паралельні гілки

[Покажчик 168 гілок GitHub](github-branches.tsv) фіксує назву, повний SHA коміту та його дерева для кожної гілки на момент зрізу. Для перегляду будь-якої версії в повному клоні можна виконати `git show <SHA>:<шлях>` або створити окрему робочу копію командою `git worktree add --detach ../knaba-variant <SHA>`.

Окремі лінії розробки змінюють ті самі міграції, кабінети та мобільні клієнти. У них зберігаються додаткові реалізації та тести.

## Відновлення трьох варіантів із робочих копій

Патчі зберігають зміни відносно конкретних комітів. Для відновлення потрібен Git-клон з історією. Остання колонка містить результат `git write-tree` після застосування до чистого індексу базової версії.

| Файл | База | Що відтворюється | Очікуване дерево |
| --- | --- | --- | --- |
| [development-20261108.patch.gz](variants/development-20261108.patch.gz) | `690a0b9c882f5a3ef5d08e83c043f39091676603` | 137 файлів паралельної розробки від 8 листопада, включно з тестовим ZIP | `49415898bde0f9323408c262896394092b2d93f2` |
| [password-policy.patch.gz](variants/password-policy.patch.gz) | `dca1ae0e2348b13b8a9a0e3721e23697e1f50ebf` | 21 файл серверної робочої версії політики паролів | `7b042532a6435982fbf2666c7761541854b1d8e6` |
| [installed-site-runtime.patch.gz](variants/installed-site-runtime.patch.gz) | `fb79ce4aba3e5645eeb8945ecd6849f33c46ccec` | Два встановлені файли сайту, `corporate-site/package.json` та `corporate-site/vps/server.mjs`. Ще 85 перевірених файлів уже збіглися з цією базою. | `4b5495bcc5a716e69fa0c9483f42598075847fe8` |

Приклад для робочого каталогу, де ще немає директорій `knaba` та `knaba-wip`

```sh
git clone --branch snapshot/knaba-source-20261121 https://github.com/ziko1/knaba.git knaba
git -C knaba worktree add --detach ../knaba-wip 690a0b9c882f5a3ef5d08e83c043f39091676603
gzip -dc knaba/docs/source-snapshot/variants/development-20261108.patch.gz | git -C knaba-wip apply --index
git -C knaba-wip write-tree
```

Для двох інших варіантів підставте у прикладі відповідний SHA бази й назву архіву з таблиці.

## Межі перевірки

Дерево сайту `d73c069adb8bfdecd16e6abbca6b65493073b8ff` пройшло 874 тести Vitest, 92 тести Node, 408 VPS-тестів, перевірку Astro та збірку з валідацією 161 HTML-сторінки. Дерево ERP `4d8bf710d521d9f231f8a3ca0fd0f7d812005958` пройшло перевірку типів і 55 перевірок Telegram, з них 15 із PostgreSQL 17.6. Для джерел серверного обслуговування виконано 16 ізольованих модульних тестів. Для переносних скриптів перевірено локальну валідацію параметрів резервування, R2, Cloudflare та Meta без зовнішніх операцій. Chromium зупинився до відкриття сторінки через обмеження Unix-сокетів у середовищі. Повний цикл ERP, встановлення на фізичних телефонах і зовнішня доставка повідомлень потребують окремої перевірки.

Production-сайт під час інвентаризації використовував артефакт SHA-256 `fe5a0cb6708b687b5ccfac4a4afbbea36cf1938562dddc15b7e3c3d086040739`, а тестовий бот — коміт `716c869f7829ca895df8a0acc729fda490c0ae15`. Облікові дані, приватні конфігурації, записи клієнтів, бази, NAS і резервні копії залишаються на боці власника.
