# Cross-module invariants and release gates

This register follows the canonical V3 specification. It is an acceptance design, not evidence of passing implementation. Every initial execution result is **NOT_RUN**. Test class separation is mandatory: a unit fixture cannot pass a provider-live or physical-device case. Tenant scope means `company_id` plus allowed customer/site/team/warehouse/self/time-limited delegation; having a role name alone is insufficient.

## Control numeric fixtures

These are synthetic test inputs, not KNABA prices, company records or legal payroll rules.

- `T-TIME-CANONICAL-01`: 08:00–12:00 WORKING A; 12:00–12:30 ON_BREAK; 12:30–13:00 TRAVELLING; 13:00–16:00 WORKING B. Chronology 480 minutes, object work 420, travel 30, break 30; synthetic paid-work-plus-travel 450 minutes. Client time remains a separate policy.
- `T-TIME-GEO-DAY-01`: 08:00–10:00 A, 10:00–10:05 AWAY_PENDING_REASON, 10:05–10:35 travel, 10:35–12:30 B, 12:30–13:00 lunch, 13:00–16:00 B. Chronology 480 minutes, object work 415, travel 30, lunch 30, unexplained 5; synthetic approved paid 445 minutes, unexplained time remains visible.
- `T-INVENTORY-CANONICAL-01`: receive 10 L at main warehouse; ship 4 L → balances main/transit/site 6/4/0; confirm receipt → 6/0/4; use 1.5 L, return and receive 0.5 L → main 6.5 L, site 2 L, usage 1.5 L, physical total 8.5 L. Replaying every command leaves numbers unchanged.
- `T-INVENTORY-SHORTAGE-01`: 4 L usable, 1 L reserved elsewhere, new need 5 L → free 3 L, shortage 2 L. After reserving those 3 L for the new demand, shortage remains 2 L. Formula `max(0, new_unreserved_demand + safety_stock − free_usable_stock − free_confirmed_inbound_by_due_date)` never double-counts reservations.
- `T-SALES-04`: 6 person-hours × EUR 30 + EUR 40 materials + EUR 20 travel = EUR 240 net; explicitly synthetic 19% adds EUR 45.60 → EUR 285.60 gross.
- `T-PAYOUT-PARTIAL-01`: approved EUR 1,000; acknowledged EUR 400 leaves EUR 600; acknowledged EUR 600 leaves zero; admin-recorded transfer without employee acknowledgment remains unconfirmed, and disputed receipt never becomes received.

## Permission coverage required before release

Each implemented command needs positive and negative execution for action/resource/scope, foreign IDs, expired delegation, role revoke, old callback/version, exported file and realtime subscription where applicable. At minimum cover `location.presence.read`, `location.live.read`, `location.history.read`, `location.policy.manage`, `timesheet.approve`, `payroll.manage`, `payout.approve`, `payout.record`, `payout.acknowledge`, `inventory.issue`, `inventory.adjust`, `procurement.approve`, `bot.settings.manage`, `chat.read/write/moderate`, `task.create/assign/review`, `site.structure.edit`, `quote.issue`, `discount.approve`, `crew.assign`, `report.publish`, and `worker_hours.share`. UI visibility alone does not pass authorization.

## Readiness language

`IMPLEMENTED` means code exists; `VERIFIED_LOCAL` means locally executed checks; `VERIFIED_STAGING` means actual permitted environment end-to-end; `RELEASE_CANDIDATE` means exact verified artifact and all available critical gates; `PRODUCTION_VERIFIED` requires authorized deploy and live smoke with disclosed unverified integrations/devices; `HANDOVER_ACCEPTED` requires actual customer acceptance/control transfer. `BLOCKED_EXTERNAL` is a specific missing dependency, not a green status. These are module readiness labels, separate from evidence results `PASSED/FAILED/NOT_RUN/BLOCKED_EXTERNAL`.
