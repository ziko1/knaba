# Accountant report handoff

`packages/integrations/accounting-export.ts` prepares `KNABA_ACCOUNTING_HANDOFF_V1` JSON from an immutable published German `report_version`. It supplies structured source facts for accountant review: frozen parties, order/quote references, performance period, accepted quantities, aggregate contractual seconds, materials and the report's existing exact EUR-cent totals.

`accountingExportSnapshot(version)` returns the minimized object. `renderAccountingExport(version)` returns UTF-8 canonical JSON bytes with a trailing newline, content SHA256, original source SHA256, report-version ID and `application/json; charset=utf-8`. Object keys are canonical; arrays preserve the published report's order. Repeated preparation of the same source produces identical bytes without a clock, database write or provider request. The content checksum identifies the download; the source checksum identifies the complete original report snapshot. They have different purposes and are not interchangeable.

The handoff explicitly says `documentType: ACCOUNTANT_REVIEW_DATA`, `legalInvoiceIssued: false`, `structuredInvoiceValidated: false` and `structuredInvoice: NOT_READY`. Report numbers stay report numbers. The adapter does not allocate invoice numbers, price performance rows, infer tax rates from totals, update invoiced/paid balances, execute payments or validate XRechnung/ZUGFeRD. Materials and quantities remain performance facts; their presence creates no additional charge. A provisional report amount is retained with an explicit finding.

## Authorization and HTTP integration

The adapter is pure and has no authority context. Its caller must require a current internal identity with `report.export`, reject any CLIENT/CUSTOMER/EXTERNAL_BAULEITER/GUEST/SERVICE_ACCOUNT role, and freshly authorize the requested `report_version` in the same company transaction. A report ID may resolve to its current published version only after authorizing both objects. Existing report-read access alone is insufficient because customers may read their published reports.

The integrated download is `GET /reports/:id/accounting-json`. Use private/no-store caching, a sanitized `.json` filename, `nosniff`, content SHA256 as ETag and the original snapshot hash as `X-KNABA-Source-SHA256`. The response contains no media rows or blob references, employee codes or timesheet IDs, payroll, bank data, GPS, comments, approval-author identities or private notes. Nested source objects are projected through allowlists; unknown address objects are represented as `addressText: null` with a finding rather than serialized. Free-text values already approved in the published report are preserved; the adapter does not inspect or redact arbitrary personal data embedded within those approved strings.

## Validation and limits

The adapter reuses `reportExportSnapshot` to check published immutable German source state, the checksum and existing report-total checks. Its additional validation requires EUR, safe integers, consistent report/site/version/template references, a positive period, accepted task rows, distinct task IDs and BigInt-exact money/hour sums. Approved change-order totals may be signed: an accepted scope reduction retains its negative `approvedChangesNetCents`. Base/final net, tax/gross, seconds and quantities remain nonnegative; the signed adjustment must still reconcile exactly to the agreed final net. It bounds each performance array to 10,000 rows and string values to 10,000 characters. It returns domain `INVALID_STATE` for invalid projected source fields; error details name fields without returning their values. The original source is hashed before projection and is never repaired or substituted with current mutable company/order data.

This is source-data validation, not verification of company facts, tax/legal applicability, an invoice schema or an accountant's approval. It does not prove that a published report is the newest report, or prevent two different published report versions from being downloaded. Downloads cause no billing effect. The HTTP layer checks current access to either the requested immutable version or the report's current version; the pure adapter deliberately receives no current company policy or mutable billing balance.

Current reports contain a tax amount and NET/GROSS presentation, but lack the authoritative frozen tax mode/rate/profile needed for invoice mapping. The export reports that tax profiles are neither exported nor inferred. Its readiness findings also state that invoice profile validation and accountant acceptance are not evaluated or recorded by this operation. EXT-01/EXT-13/EXT-19 in `EXTERNAL_PREREQUISITES.md` remain applicable. An agreed XRechnung/ZUGFeRD profile, current official validator, confirmed company/customer tax data and accountant acceptance need a separate adapter and external evidence.
