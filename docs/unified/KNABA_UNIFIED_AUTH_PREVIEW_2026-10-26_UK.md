# KNABA — єдиний вхід і реєстрація: кандидат (26.10.2026)

**Гілка:** feat/knaba-unified-signin-registration-20261026 на точному стані Draft PR #107 8fff82844d65d8e4accdc434c7b7211e50f4a903. Це не production-ready реліз.

## Причина «Anmeldung fehlgeschlagen»
- На попередній тестовій версії KNABA VPS було лише /login/, а /register/ повертало 404; в актуальній тестовій БД був лише один обліковий запис.
- HTML minlength 16→8 прибрало перевірку браузера, але НЕ створило облікового запису і не змінило пароль. Вхід неіснуючого користувача повертає однакове 401 без розкриття email.
- Ні паролі, ні сесії, ні власницький доступ не скидаються або не видаються для обходу авторизації.

## Реалізовано на основі наявних PR #102/#107/#108
- Єдиний /login/ та /register/ зі справжніми DE/UK/EN/RU локалізаціями й мовною навігацією.
- Для входу до існуючого облікового запису HTML-мінімум 8 символів. Створення/оновлення нових паролів за чинною політикою безпеки PR #107 вимагає 16–256 символів — це не те саме, що вхід.
- Мобільний адаптивний інтерфейс від 320 px, доступні focus, ARIA alert та чекбокс; browser/device acceptance ще потрібно перевірити.
- У разі невдалого входу пропонується контакт і реєстрація за запрошенням, але не розкривається факт існування адреси.
- Фрагмент одноразового запрошення зберігається між перемиканнями мов, але не потрапляє до HTTP GET/query, а браузерна історія очищається.

## Матриця ролей — сервер як джерело істини
| Суб'єкт | Роль до затвердження | Активування |
| --- | --- | --- |
| Гість | anonymous | публічні ресурси |
| Власник | окремий owner invite і перевірена особа | спеціальна захищена активація |
| Клієнт | pending, requestedRole=client | згода власника у порталі |
| Працівник | pending, requestedRole=worker | згода власника у порталі |
| Адміністратор | ніколи через відкриту форму | окреме затвердження власником |

Зміна POST поля role або status не може дати admin/owner/worker; у Worker/Portal обов'язкове підтвердження approved profile. Заявлена роль формується із перевіреного одноразового запрошення, а не вибирається довільно клієнтом.

## Обмеження та наступні gates
- Відкритий self-signup із доведенням володіння email не активовано: KNABA поки не має перевіреного авторизованого sender/OIDC/OTP. Без запрошення активний акаунт не створюється.
- Forgot-password без існуючого сеансу, компанійний identity bridge до ERP, GDPR, live owner UAT, незалежний security review і фізичні пристрої потребують окремих доказів.
- Жодні секрети, email та запрошення не повинні потрапляти в source/логи. Main merge, production, офіційний knaba.de і ERP не змінювати.

## QA та міграції
- Новий Auth UI: RED 1/1, GREEN 1/1 на реальному локальному HTTP+SQLite+Worker.
- Повний VPS: 60/60 PASS у Node 24.22.1 з KNABA_RELEASE_MODE=vsp, включно з інвайтами, pending/approval, CSRF, role forgery, replay.
- Site npm run check: 0 errors/warnings (4 hints), npm test, npm run build, npm run verify:build — exit 0.
- Чинна SQL ledger: 6/6 міграцій точно збігаються, SQLite integrity=ok; 0006 та 0007 additive. Приватну незмінну резервну копію створено й перевірено, її тестова копія пройшла upgrade 6→8, наявний обліковий запис не втрачено.
- Немає фактичного входу реального користувача, перевіреного власника чи підтвердженого email sender; не називати це production-готовим.

## Дозволений порядок release
1. Source та QA у Draft PR; точна Git identity й independent review.
2. Перевірити backup + rollback, готовність owner, поточну live ledger.
3. На дозволеному тестовому preview застосувати тільки additive міграції, потім source/candidate з контролем rollback.
4. Перевірити HTTP 200 та security flows на синтетичних акаунтах, mobile/browser UAT.
5. Відкрита реєстрація і парольне відновлення — тільки після перевіреного каналу підтвердження email та юридичних gates.
