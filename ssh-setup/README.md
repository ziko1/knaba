# SSH: перевірка та початкове налаштування сервера

Невеликий Bash-скрипт для **Ubuntu та Debian із systemd**. Запускається **на самому сервері** через консоль хостингу або наявний доступ адміністратора.

## Запуск

Завантаження має завершитися успішно до запуску скрипта. Виконай одним рядком:

```bash
ssh_setup=$(curl -fsSL https://raw.githubusercontent.com/ziko1/knaba/ssh-setup/ssh.sh) && sudo bash -c "$ssh_setup"
```

Адреса веде на окрему гілку `ssh-setup`; для фіксації перевіреної версії можна замінити назву гілки на повний SHA опублікованого коміту. Якщо консоль уже відкрита під `root`, прибери `sudo`.

Для перегляду без змін:

```bash
ssh_setup=$(curl -fsSL https://raw.githubusercontent.com/ziko1/knaba/ssh-setup/ssh.sh) && sudo bash -c "$ssh_setup" -- --check
```

У варіанті з `bash -c` аргумент `--` займає позицію `$0`, а `--check` передається скрипту як `$1`. Завантажений скрипт також можна зберегти як `ssh.sh` та виконувати `sudo bash ssh.sh --check`. Довідка: `bash ssh.sh --help`.

## Що виконується

1. Перевіряє, що це Ubuntu/Debian, є права root і працює systemd.
2. Перевіряє стандартний спосіб запуску служби. Для нестандартного `ExecStart`, параметрів `-f`/`-o`/`-p`, додаткових `EnvironmentFile` або непорожнього `SSHD_OPTS` зупиняється для ручної перевірки.
3. У режимі налаштування встановлює `openssh-server`, якщо відсутній виконуваний файл `sshd`.
4. Якщо основного конфігураційного файлу немає, створює `/etc/ssh/sshd_config` зі штатного шаблону пакета. У цьому випадку `ssh-keygen -A` також створює відсутні серверні ключі. Наявні конфігураційні файли та ключі використовуються як є.
5. Перевіряє конфігурацію та ключі через `sshd -t`, потім вмикає службу або наявну сокет-активацію SSH. Встановлення пакета також може запускати службу через його штатні сценарії.
6. Показує параметри, прочитані з файлів, стан служби/сокета та фактичні TCP-порти.

Режим `--check` лише читає стан: не встановлює пакети, не створює файли чи ключі та не змінює стан служб. Якщо відсутні необхідні файли або `/run/sshd`, перевірка повідомить про помилку.

## Підключення з Android

У SSH-клієнті, наприклад Termius, вкажи IP із панелі хостингу, фактичний порт SSH і наявний логін сервера. Спосіб входу визначається налаштуваннями облікового запису: пароль, ключ або їх поєднання. Створені серверні ключі підтверджують особу сервера; вони не є ключем доступу користувача. Вхідний порт SSH має бути дозволений у чинному firewall сервера та хостингу.

| Параметр | Значення |
| --- | --- |
| `port` | Порт із конфігураційних файлів. За сокет-активації звіряй із активним `Listen` та фактичними сокетами. |
| `passwordauthentication yes` | Дозволений метод входу за паролем. |
| `pubkeyauthentication yes` | Дозволений метод входу за ключем. |
| `permitrootlogin prohibit-password` | Парольний вхід під root заборонений. |
| `authenticationmethods publickey,password` | Потрібні обидва методи послідовно. |
| `allowusers` / `allowgroups` | Додаткові обмеження користувачів або груп. |

`sshd -T` показує конфігурацію з файлів на диску. Запущений процес може ще використовувати попередню конфігурацію. Правила `Match` можуть змінювати умови для конкретного користувача/IP; для їх точної перевірки потрібні параметри з’єднання через `sshd -T -C`.

Скрипт не створює облікових записів і паролів. Він не змінює політику автентифікації, не перезапускає чинний процес SSH, не знімає `masked` і не змінює firewall. Для пошкодженої конфігурації, нестандартного способу запуску або відсутніх власних ключів потрібен окремий розбір стану сервера.


Тести використовують ізольовані підміни системних команд. Результати та межі перевірки: [VALIDATION.md](VALIDATION.md).
