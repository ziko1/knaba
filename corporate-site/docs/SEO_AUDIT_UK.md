Контактні дані беруться з наявного централізованого `company.ts`; агент контенту їх не змінює. Юридичні дані й політику конфіденційності перевіряє окрема гілка роботи. Не додано нових офісів, годин роботи, сертифікацій, чисельності персоналу, відгуків, рейтингів, цін або гарантованого строку відповіді.

## 4. Реалізований зміст R3

- Шість сторінок послуг: окремий заголовок і description, оригінальний вступ, змістовні пояснення, перелік робіт, список даних для підготовки, три релевантні відповіді на питання, контактний заклик і посилання на відповідний матеріал.
- `/ratgeber/` та чотири повні статті. Статті мають навігацію по розділах, практичну пам'ятку, посилання на потрібну послугу та інші матеріали.
- `/berlin/`: одна змістовна регіональна сторінка з підтвердженим контактом і умовами планування. Не створено дублікати під кожний район і не вигадано локальні філії.
- Дані централізовані в `src/data/seo-content.ts`. Кожна сторінка передає конкретні метадані, видимі breadcrumbs та відповідну структуру Service / Article / CollectionPage у спільний Layout.
- Текст доступний у HTML після prerendering. Контент і переходи не залежать від завантаження кабінету чи входу користувача.

Слово «професійний» не підміняє факти: текст не заявляє медичних гарантій, статусу Meisterbetrieb, сертифікацій, страхових сум чи непідтвердженого досвіду в роках. Розділи про ціни описують фактори, а не вигаданий прайс.

## 5. Технічне SEO: вимоги до інтеграції

Ці перевірки належать інтеграційному прийманню; наявність пункту в аудиті не означає, що він уже пройшов на живому домені.

| Перевірка | Очікувана поведінка / спосіб приймання |
| --- | --- |
| Titles, descriptions, H1 | Унікальні, німецькою, відповідають фактичному вмісту; один H1; HTML-перевірка всіх сторінок |
| Canonical | Узгоджений абсолютний URL без параметрів фільтрів/вибору; під час міграції змінюється origin одним конфігом |
| Sitemap | У режимі офіційного релізу містить публічні канонічні сторінки, зокрема нові 6 URL; не містить приватні кабінети й API. На тимчасовому домені sitemap навмисно порожній |
| Structured data | LocalBusiness із підтвердженими даними; Service для послуг, Article для статей, BreadcrumbList. Без вигаданих review/rating/price даних |
| Internal links | Послуга → пов'язаний матеріал → заявка; індекс матеріалів; URL перевірені у зібраному артефакті |
| Client navigation | Зміна URL, title, canonical і вмісту при переході без повного перезавантаження; працездатне відкриття прямого посилання |
| Accessibility / mobile | Семантичні заголовки, клавіатура, читабельна ширина статті, відсутність горизонтального переповнення |
| Localization | `lang="de"`; коректні німецькі підписи. `hreflang` тільки для реальних повних перекладів, не для неіснуючих URL |
| Search Console | Підключення й submission лише для перевіреного офіційного property після випуску; не вважати саму наявність sitemap індексацією |

### Тимчасовий домен і robots

Тимчасова версія має лишитися `noindex` до погодженої міграції. Google вказує, що для читання `noindex` crawler має мати доступ до сторінки. Тому одночасний глобальний `Disallow: /` не є надійним способом змусити Google побачити цю директиву. Рекомендовано дозволити crawl публічних preview-сторінок і передавати `noindex` у HTML/HTTP; приватні дані захищати авторизацією, а не robots. Джерело: [Google: Block Search indexing with noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing), 24.10.2026.

Інтеграційне рішення R3: публічний preview використовує `noindex, follow` із дозволеним crawl, а sitemap тимчасово не містить URL. Це зберігає підготовлену структуру для офіційного випуску, не заявляючи, що тимчасовий дубль уже приносить пошуковий трафік.

Наявність JSON-LD не гарантує спеціальний вигляд результату. Старе посилання Google на FAQ structured data під час перевірки перенаправляло на [журнал оновлень](https://developers.google.com/search/updates); видимі FAQ залишаються корисними для читача, без обіцянки FAQ rich result.

## 6. Наступний крок після міграції на knaba.de

1. Перевірити правові реквізити, умови реальних послуг і доступ власника; прийняти остаточний контент.
2. Узгоджено змінити origin, canonical, sitemap і правила індексації. Зберегти обмеження приватних кабінетів.
3. Підготувати постійні redirect для старих URL на відповідні сторінки. Не перенаправляти всі старі сторінки на головну без відповідності змісту.
4. Перевірити офіційний Search Console property, надіслати sitemap; окремо перевірити індексацію важливих URL. Публікація не дорівнює індексації.
5. Перевірити єдині назву, адресу й телефон у погодженому бізнес-профілі. Додавати лише власні фото, реальні кейси й відгуки з належними правами.
6. Через доступний період даних переглянути запити, покази, кліки й заявки; розширювати контент за реальними питаннями клієнтів і пропущеними намірами.
