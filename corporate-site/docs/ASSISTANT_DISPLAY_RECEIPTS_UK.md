# Підтвердження показу повідомлення власника у гостьовому чаті

Дата: 2026-11-08. Локальний кандидат KN-C05; незалежне review, інтегрована збірка та browser acceptance мають окремі докази.

## Значення позначки

`guestDisplayedAt` — серверний час першого прийнятого повідомлення клієнта про показ конкретного повідомлення власника у видимій частині гостьового чату. Це не доказ людського прочитання, доставки через email/WhatsApp, згоди з пропозицією або виконання бізнес-дії. Власник бачить «Показано в чаті відвідувача» з часом або «Показ у чаті відвідувача не підтверджено». Підписи доступні шістьма мовами.

Клієнтський звіт не може довести, що людина дивилася на екран. API доводить лише наявність чинного доступу до цієї розмови та належність указаних повідомлень власнику. Окреме прийняття/відхилення пропозиції збережено без змін.

## HTTP і база даних

`POST /api/assistant/conversations/:id/displayed` приймає JSON `{ "messageIds": ["<uuid>"] }`, від 1 до 32 різних UUID. Потрібні чинний `X-KnaBa-Conversation`, same-origin JSON та чинний `X-KnaBa-Request`. Вхід власника без гостьового capability не дає права підтверджувати показ.

Усі IDs мають належати повідомленням `sender='owner'` саме цієї розмови. Запис одним SQL statement перевіряє всю групу та поточний capability; неправильний ID не спричиняє часткового запису. Capability повторно перевіряється при читанні результату та перед відповіддю. Відкликаний, прострочений, неправильний або відсутній код отримує однакову 404 без приватного payload. Некоректна форма групи отримує 422 після перевірки доступу.

Відповідь: `{ "receipts": [{ "id": "<uuid>", "guestDisplayedAt": "<ISO timestamp>" }] }`. Текст повідомлень, контакти та токени до неї не копіюються. Поле також додається до повідомлень у чинній відповіді thread API.

Міграція `0016_assistant_display_receipts.sql` додає nullable `assistant_messages.guest_displayed_at`. Старі повідомлення залишаються `NULL`; дата не виводиться з історичних GET, створення чи доставки. Тригери дозволяють тільки канонічну ISO-дату для повідомлення власника та зберігають перший час незмінним. Повторний однаковий запит ідемпотентний. Ідентифікатор повідомлення та його розмову після встановлення позначки також не можна перепризначити.

Перегляд не змінює `assistant_conversations.updated_at`, статус розмови або порядок inbox. Закриту розмову можна переглядати з чинним capability; закриття не дорівнює відкликанню. Немає нового notification/outbox, provider call, ERP-копії, журналювання токенів чи контактів.

Drizzle metadata зберігає всі 22 попередні таблиці; 16 старих migration receipts та journal entries не переписуються. Запуск на старій БД без дозволу міграції завершується повідомленням про pending 0016. Перевірки включають оновлення зі старих схем, збереження даних, integrity/foreign keys та повторне відкриття БД.

## Клієнтський життєвий цикл

Гостьовий компонент планує перевірку після двох animation frames. Перед відправленням він повторно перевіряє відкритий widget, `document.visibilityState`, поточний ticket і належність thread до цього ticket. DOM-вузол повідомлення власника має бути підключений і перетинати область прокрутки чату та видимий viewport. Враховано visual viewport мобільної клавіатури. GET або фоновий poll сам по собі не підтверджує показ.

Перевірку запускають оновлення thread, відкриття чату, scroll, visibility та зміни viewport. Одночасно виконується один receipt request; максимум 32 IDs, наступна група — після успіху та нових двох frames. Підтверджені IDs зберігаються лише в пам'яті цього екземпляра та capability. Після помилки повторні спроби дозволено не частіше одного разу за 8 секунд, у ритмі чинного polling.

Reset, unmount або зміна ticket скасовують старий запит і змінюють generation. Пізня відповідь чи animation callback не можуть очистити нову розмову, підтвердити її чужим capability або відновити старий приватний стан. Чинна receipt 404 очищає приватний ticket/history за наявним контрактом, зберігаючи незавершений текст. Мережевий збій/5xx не очищає чат і не показується як успіх.

Сумісність: якщо старий server thread payload не містить нового nullable поля, клієнт не викликає новий receipt endpoint. Старий клієнт може й далі отримувати thread та писати повідомлення; зайве поле не змінює ці контракти.

## Докази та межі

Докази цього зрізу зберігаються у `verification/assistant-display-receipts/` поряд із checkout: вихідні backend/migration RED, цільові SQLite/API, HTTP, async/visibility, локалізаційні тести та manifest із SHA-256 джерел. Git HEAD сам по собі не є доказом незакомічених файлів.

Окремо залишаються: незалежне review, інтегрований JS/CSS budget, реальна браузерна перевірка показу/scroll/visibility, owner UAT, зовнішні канали та conversation→ERP bridge із явною згодою. Цей зріз не закриває всю KN-C05 або whole-product acceptance.

Rollback: зберегти адитивну колонку, тригери, історію й migration ledger; повернути попередній сумісний runtime або вимкнути UI-відправлення receipt. Після старого runtime нові покази не підтверджуватимуться. Видалення або обнулення історичних позначок не потрібне.
