# KNABA — експлуатація налаштувань користувача

Дата: 08.11.2026. Документ описує реалізований кандидат модуля; він не засвідчує його встановлення на сервері чи доставку реальних листів. Фактичні результати перевірок і точну ревізію зберігає [основний запис задачі](../../docs/unified/USER_SETTINGS_2026-11-08_UK.md).

## 1. Межі модуля та передумови

Модуль працює в чинному VPS runtime KNABA: Node.js 24, локальна SQLite, наявні облікові записи `vps_users` і захищені сесії `vps_sessions`. Він додає налаштування до наявної авторизації, не створює другого каталогу користувачів і не змінює права доступу через поля профілю.

| Середовище / тип акаунта | Поведінка |
| --- | --- |
| VPS, локальний пароль | Профіль, контактні дані, мова, часовий пояс, зміна пароля, керування власними сесіями; відновлення пароля й підтвердження нового email залежать від налаштованої пошти |
| VPS, Google/Microsoft OIDC | Налаштування власного профілю й сесій доступні; самостійна зміна login-email заблокована, оскільки чинна прив’язка перевіряє email провайдера |
| Власник / розробник із захищеною адресою | Профіль і пароль можна змінювати; login-email потребує окремої перевіреної адміністративної процедури, а не форми самостійного редагування |
| Hosted ChatGPT Sites, `PUBLIC_KNABA_AUTH_MODE=sites` | Авторизація залишається native ChatGPT; VPS-модуль не змінює пароль OpenAI та не переносить його в SQLite |
| ERP / PostgreSQL / native mobile | Цей модуль не об’єднує site/ERP principals і не створює спільний SSO. Їхні незавершені identity-контракти зберігаються окремо |

Для OIDC-користувача відновлення через цей модуль встановлює локальний пароль KNABA після підтвердження володіння його скринькою. Воно не змінює пароль Google/Microsoft і не відв’язує OIDC.

Перед запуском потрібні: точний перевірений source/artifact, правильний приватний `KNABA_DB_PATH`, наявні owner/developer bindings, HTTPS і перевірена конфігурація reverse proxy. Залишити `KNABA_LOCAL_TEST` вимкненим на робочому сервері. Перевірити достатність місця для backup і міграції, а також зупинити конкурентні процеси міграції. Зовнішній поштовий сервіс, production deployment та зміни реальних даних потребують чинного дозволу саме на відповідну дію.

Джерела: [server.mjs](../vps/server.mjs), [hosting-auth.ts](../src/lib/hosting-auth.ts), [account-settings.mjs](../vps/account-settings.mjs).

## 2. Конфігурація пошти

Параметри зберігаються лише в захищеному серверному environment/secret store. Не передавати ключі як аргументи команд, у браузер, Git, PR, знімки екрана або журнали.

| Змінна | Вимога чинного коду |
| --- | --- |
| `KNABA_ACCOUNT_EMAIL_ENABLED` | Рівно `approved`. Інше значення або відсутність вимикає account mail |
| `KNABA_ACCOUNT_EMAIL_FROM` | Валідна адреса відправника або формат `Назва <адреса>` без переносів рядка; відправника потрібно окремо перевірити в акаунті провайдера |
| `RESEND_API_KEY` | Непорожній захищений ключ Resend; не більше 4096 символів, без CR/LF |
| `KNABA_ACCOUNT_EMAIL_DAILY_LIMIT` | Ціле число від 1 до 100 включно. Встановити в межах фактично підтвердженої квоти й дозволеного бюджету |
| `KNABA_PUBLIC_ORIGIN` | Довірена HTTPS origin саме цього deployment. Сервер передає її в mailer; адреса з користувацького поля або довільного HTTP-заголовка не використовується для посилань |
| `KNABA_DB_PATH` | Абсолютний шлях до правильної постійної SQLite цього KNABA runtime |
| `KNABA_BACKUP_DIR` | Захищений каталог резервних копій для чинного CLI; типовий шлях у коді — `/var/lib/knaba/backups` |

Наявність коректних рядків конфігурації означає лише, що адаптер може бути увімкнений. Верифікація домену відправника, реальна квота, тариф, дозволені адресати й доставка до скриньки **не перевіряються цим прапорцем**. Їхній стан до окремої перевірки — `UNKNOWN`. Не вмикати інші notification-модулі разом із account mail як побічну дію.

### Межі й результат відправлення

- Endpoint зафіксований у коді: `https://api.resend.com/emails`; перенаправлення заборонені.
- Одна спроба має верхню межу 5 секунд; тіло відповіді обмежене 8192 байтами.
- До 4 одночасних provider requests. Для публічного відновлення також до 4 прийнятих in-process задач без необмеженої черги.
- Публічний reset відповідає після перевірки та bounded scheduling, не очікує provider I/O. Відсутня, неактивна й обмежена адреса отримує ту саму загальну відповідь.
- Ліміти reset перевіряються в порядку: джерело — 10 запитів за 15 хвилин; адреса — 3 за годину; спільний request budget — 120 за годину. Зміна email має 5 спроб на користувача за 15 хвилин.
- Reset і зміна email спільно використовують налаштований добовий delivery budget у SQLite; вікно — UTC-доба. Резервування спроби не є доказом фактичного списання чи доставки.
- Автоматичних повторів немає. Запит має `Idempotency-Key`, але після невизначеної відповіді повторна автоматична відправка не запускається.
- `accepted` означає HTTP success із валідним provider receipt ID. `unknown` означає, що достовірного підтвердження немає; це не звіт про доставку. Одноразове посилання зі станом `unknown` можна використати, якщо лист фактично надійшов і всі перевірки повноважень залишаються чинними.
- За остаточної відмови, вимкнення доставки або втрати актуальних повноважень відповідна capability видаляється/стає непридатною. Зміни профілю й пароля не застосовуються на підставі самого факту запиту листа.

Raw-token outbox не створюється. Планування відновлення є частиною запущеного серверного процесу, не окремим daemon чи гарантованою чергою після restart. Після зупинки процесу незавершений запит може потребувати повторного запиту користувача; не називати `202` підтвердженням отримання листа.

Джерела: [account-mail.mjs](../vps/account-mail.mjs), [requestPasswordReset / requestEmailChange](../vps/account-settings.mjs).

## 3. Посилання, пароль і сесії

Вхід до налаштувань: `/account/settings/?lang=uk`. Підтримувані мови: `de`, `en`, `pl`, `lt`, `ru`, `uk`. Стандартна зміна пароля зберігається на `/account/password/` і потребує поточного пароля.

Відновлення починається на `/forgot-password/`. Лист використовує `/reset-password/?lang=uk#token=…`; підтвердження нової адреси — `/account/email/confirm/?lang=uk#token=…`. Токен знаходиться у fragment, який браузер не надсилає серверу як частину HTTP URL. Сторінка переносить його у форму й очищає fragment з поточної адреси; передбачено ручне введення коду. Query-параметри секрету не приймаються. Не копіювати повні посилання в операційні журнали, аналітику, issue чи support screenshot.

Токени мають 256 біт випадковості, строк 30 хвилин, одноразове використання й SHA256-представлення в SQLite. Вони прив’язані до конкретного користувача, старого email, актуальних credentials і версії/стану профілю. Зміна профілю може вимагати нового посилання. Email change додатково вимагає живої сесії, з якої розпочато операцію; вихід із цієї сесії робить посилання непридатним.

Новий пароль має 8–256 символів, збігатися з підтвердженням і відрізнятися від чинного. Успішна зміна/скидання пароля або підтвердження нового email атомарно змінює credentials, видаляє всі сесії цього користувача й інші outstanding account tokens та додає запис audit. Автоматичний вхід після reset не виконується. Ролі, схвалення та доступ до компаній не підвищуються.

У списку сесій показується максимум 100 активних записів, включно з поточним, і точна загальна кількість. Кнопки завершення інших/усіх сесій охоплюють усі власні сесії. Ідентифікатори для UI не є bearer tokens і не є сирими серверними token hashes.

## 4. Міграція й резервна копія

### Що змінює схема

Окремий VPS-auth крок додає `vps_account_settings`, `vps_account_tokens`, індекси та triggers `vps_account_tokens_user_revoke` і `vps_account_tokens_profile_revoke`. Triggers відкликають account tokens при зміні credentials/email/disabled або email/role/status профілю. Чинні Drizzle SQL-файли, їхні контрольні суми й порядкова історія не переписуються.

Звичайний запуск VPS із відсутніми account tables/triggers зупиняється з `Pending VPS auth migration account-settings`. Це навмисна відмова до явної міграції. Не обходити її встановленням `KNABA_LOCAL_TEST=1` на робочому сервері.

### Порядок підготовки

1. Зафіксувати source SHA, artifact hash, поточний deployment і фактичні приватні шляхи даних. Спочатку виконати rehearsal на ізольованій staging-копії; production тут не підміняти локальними тестами.
2. Підготувати незалежну SQLite online backup зі старого сумісного release, зберегти її контрольну суму та захищену копію поза каталогом release. Не копіювати лише відкритий основний `.sqlite` без урахування WAL.
3. Відновити backup в окремий шлях і перевірити цілісність, відповідність ledger та збереження потрібних даних. Контрольна сума файла сама по собі не доводить відновлюваність.
4. За наданого дозволу зупинити приймання нових записів для цільового cutover, виконати міграцію саме з прийнятого кандидата, потім audit і приймальні сценарії.

### Наявні CLI-команди

Нижче наведено чинний CLI, а не виконані в цьому документі операції. Команди запускаються з `corporate-site/` відповідного release на Node.js 24, коли захищений environment уже вказує на перевірені шляхи цільової БД і backup. Не покладатися на типовий `KNABA_DB_PATH`, якщо він не звірений.

До міграції, **зі старого сумісного release**:

```bash
node vps/manage.mjs audit
node vps/manage.mjs backup
```

Із прийнятого нового кандидата, спочатку на staging:

```bash
node vps/manage.mjs migrate
node vps/manage.mjs audit
node vps/manage.mjs backup
```

`backup` використовує SQLite online backup, встановлює права `0600` і повертає шлях, SHA256, bytes та migration names. Нова версія `backup` відкриває БД з `allowMigrations:false`: до account-auth upgrade вона може відмовити через pending schema. Тому початкову незалежну копію треба отримати сумісним попереднім release.

`migrate` перед зміною непорожньої БД створює додаткову `pre-migrate-*.sqlite` online backup з SHA256 і правами `0600`, а потім виконує дозволені forward migrations. Його повідомлення про backup не є окремим restore-test. При критичному браку місця CLI backup/migrate відмовляється продовжувати. `audit` відкриває існуючу БД read-only, виводить ledger, назви таблиць і `PRAGMA integrity_check`; він не перевіряє бізнес-сценарії та не створює акаунтів.

Готової команди `node vps/manage.mjs restore` у цьому репозиторії немає. Для staging restore оператор відновлює перевірену копію на окремий шлях затвердженим backup-інструментом, після чого спрямовує `KNABA_DB_PATH` на цю копію й запускає наявний `audit`. Production restore потребує окремого review плану, узгодження write window і відновлення актуального стану credentials/revocations.

Джерела: [database.mjs](../vps/database.mjs), [manage.mjs](../vps/manage.mjs), [migration-upgrade.test.mjs](../vps/migration-upgrade.test.mjs).

## 5. Rollback без повернення старих паролів

Перший спосіб відновлення після дефекту — виправлений сумісний код або перевірений rollback коду зі **збереженням актуальної БД**, її credentials, email, відкликань і audit. Після початку роботи користувачів backup до міграції вже може містити старі паролі та сесії. Відновлювати його поверх актуальної БД як звичайний спосіб відкату цього модуля заборонено: це може скасувати зміни пароля й відкрити раніше завершені сесії.

Перед rollback коду перевірити його сумісність із новими таблицями/triggers на копії, зберегти поточний backup і зафіксувати точні версії. Не видаляти нові таблиці, triggers чи ledger, щоб змусити старий binary запуститися. Перед поверненням трафіку перевірити: актуальний пароль працює, попередній не працює, старі сесії й використані посилання не відновилися.

Якщо пошкодження вимагає повного restore старішої копії, залишити сервіс недоступним для звичайного входу до окремого плану відновлення безпеки: звірити й зберегти останній достовірний credential/email state та revocations або провести перевірене повторне відновлення доступу для уражених користувачів. Готової масової процедури такого перенесення credentials у модулі немає; це `HOLD`, доки її не підготовлено та не перевірено. Наявність backup не дає дозволу повертати старі паролі чи автоматично розсилати листи всім користувачам.

## 6. Поведінка при вимкненій пошті

Відсутня або неповна mail-конфігурація не перешкоджає редагуванню профілю, зміні відомого поточного пароля та керуванню сесіями. `/forgot-password/` показує, що відновлення через email недоступне, і пропонує перевірений контакт KNABA. Форма зміни email недоступна; чинна адреса зберігається. Спроба POST до вимкненої поштової операції отримує `503`, а не вигадане підтвердження відправлення.

Не обіцяти користувачеві лист за відсутності підтвердженої доставки. За втрати доступу й вимкненої пошти використовується окрема перевірка особи через довірений канал; цей документ не задає універсального пароля, обходу входу або автоматичного надання ролі.

## 7. Матриця приймання staging

Таблиця — план перевірки конкретного deployment. До запису фактичного target/SHA/artifact, кроків і evidence її стан — `NOT_RUN`; локальні synthetic HTTP/SQLite/transport тести не замінюють ці сценарії.

| Область | Критерій на цільовому staging | Потрібний доказ |
| --- | --- | --- |
| Схема й дані | Без міграції normal startup відмовляє; після дозволеної міграції чинні користувачі, ledger й бізнес-дані збережені | Backup digest, незалежний restore, audit, точний source/target |
| Профіль | Дозволені поля зберігаються після reload/restart; стара форма не перезаписує новішу | Реальний browser → HTTP → SQLite сценарій, конфлікт версії |
| Ізоляція | Клієнт/worker/partner/bauleiter/admin змінює тільки власні налаштування; user ID, role і grants з форми відхиляються | Два окремі тестові акаунти, негативні запити та перевірка незмінності чужих записів |
| Власник / OIDC | Name власника без profile зберігається без створення ролі; захищений або OIDC login-email не змінюється формою | Перевірені типи акаунтів, UI/error і DB assertions |
| Пароль | Зміна з поточним паролем завершує всі попередні сесії, старий пароль відхиляється | Дві браузерні сесії та новий login; без запису паролів у evidence |
| Recovery | Для існуючої/відсутньої адреси однакова відповідь; дозволений тестовий одержувач реально отримує лист; replay/expiry не працюють | Окремий дозвіл на відправлення, provider receipt і фактичне отримання без збереження токена |
| Email change | Старий email чинний до підтвердження; після підтвердження новий login працює, роль/ID збережені; відкликана сесія блокує старе посилання | Контрольована нова скринька, дві сесії, audit і DB evidence |
| Mail unavailable / unknown | Disabled не надсилає листів; provider timeout не викликає retry або фальшивий success | Контрольований staging transport/provider сценарій, bounded request count |
| Сесії | Власні opaque handles не дають відкликати чужу сесію; others/all працюють і при понад 100 записах | Окремі акаунти та перевірка поточної/іншої сесії |
| UI і локалізація | Шість мов, мобільна ширина, keyboard/focus, помилки й ручне введення коду; немає витоку токена в URL query/referrer | Скріншоти й browser interactions на точному artifact |
| Rollback | Актуальний пароль і відкликання збережені після дозволеного відновлення коду | Rehearsal на копії й перевірка негативного входу старим паролем |

Відповідальні за активацію фіксують стан квоти, дозволений добовий cap, перевіреного відправника та тестового одержувача перед першим зовнішнім листом. `accepted` адаптера, зелені unit tests і здоровий `/healthz` самі по собі не закривають реальну доставку чи приймання модуля користувачем.

Технічні сценарії для відтворення: [account-settings.test.mjs](../vps/account-settings.test.mjs), [account-mail.test.mjs](../vps/account-mail.test.mjs), [account-settings.http.test.mjs](../vps/account-settings.http.test.mjs), [account-settings-ui.test.mjs](../vps/account-settings-ui.test.mjs).
