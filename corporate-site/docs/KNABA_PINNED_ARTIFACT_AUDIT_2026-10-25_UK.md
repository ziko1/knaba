# KNABA — безпечна перевірка побайтової тотожності релізу

Дата: 25 жовтня 2026. Сфера: тільки developer preview `kneba.vsp.rest`, **без** зміни `knaba.de`, DNS, БД, та `main`.

## Дефект, який відтворено

Під час попередньої перевірки порівнювали хеші з різних випусків: `/srv/knaba/vps/current` — змінне символічне посилання. Поки йшла перевірка, незалежний release-процес кілька разів переключав `current`. Факт зміни зафіксовано: під час того самого сеансу `current` вказував послідовно на `7f886606...` і `7e774c32...`. Таке порівняння не доводить ані помилки файлів, ані тотожності.

Для фактично збереженого релізу `7f886606d5711ac93a88d3d93b54a0a9b5638525` верифікатор побайтової збірки і запуск у Node24 дали **той самий** SHA256:
`c05519f298821574679f1061bf13c3eb20578b85c9c206e7b9433dd9a428cd6d` (160 файлів / 103 HTML).

**Не** заявляти, що будь-який новий `current` має той самий хеш без перевірки конкретного SHA та його власного маніфесту.

## Новий read-only gate

Файл: `corporate-site/scripts/verify-live-artifact.mjs`. Тест: `corporate-site/tests/verify-live-artifact.test.mjs`.

Параметри повинні бути явними й незалежно перевіреними:
- `--releases`: абсолютний шлях до каталогу незмінних релізів;
- `--current`: абсолютний шлях до символічного посилання активної версії;
- `--source`: очікуваний SHA40 вихідного коміту релізу;
- `--artifact`: SHA256 конкретної збірки з перевіреного receipt (не приблизний hash джерел чи старого релізу).

Команда від імені користувача, який має лише права читання:

```bash
node corporate-site/scripts/verify-live-artifact.mjs \
  --releases /srv/knaba/vps/releases \
  --current /srv/knaba/vps/current \
  --source <EXACT_40_CHAR_RELEASE_SHA> \
  --artifact <EXACT_64_CHAR_BUILD_SHA256>
```

Не копіюйте прикладові SHA у живий виклик замість фактичних значень; обидва беруться з доказової квитанції того самого релізу. Не потрібно `sudo`, Docker restart, доступу до SQLite чи ключів.

Скрипт:
1. Фіксує об'єкт з `releases/<source>`, перевіряє, що `current` вказує саме на нього.
2. Читає **тільки** `<pinned-release>/dist/client`, відкидає symlink або незвичайні файли.
3. Хешує за **точним контрактом** `tests/verify-build.mjs`: відсортований відносний шлях + NUL + двійкові байти файла + NUL.
4. Перевіряє стабільність кожного файла і списку файлів, потім повторно читає `current` разом із його inode/ctime.
5. Лише після цих перевірок порівнює незалежний очікуваний SHA256.

## Класи результатів і дії

- `PASS`: правильні SHA джерела й артефакта за незмінного pointer/файлів.
- `WRONG_RELEASE`: уже переключено на інший SHA; перечитати фактичний HEAD і його квитанцію.
- `RELEASE_SWITCHED`: перемикання відбулося під час перевірки (включно з A→B→A); **не** повідомляти «пошкодження збірки».
- `RELEASE_MUTATED`: змінився файл, файлова метаінформація або перелік файлів; не приймати реліз.
- `ARTIFACT_MISMATCH`: pointer і дані залишалися стабільними, але байти не відповідають незалежно наданому SHA; розслідувати source-to-artifact provenance.
- `UNSAFE_SYMLINK`, `UNSAFE_CURRENT`, `UNSAFE_RELEASE`, `INVALID_INPUT`: відхилення без довільного читання поза релізом.

Не виправляти жодний FAIL «підстановкою фактично обчисленого хешу» замість перевіреного очікуваного. Не видаляти старі релізи, backup або SQLite.

## Реальний QA / red-green

- RED: сім базових тестів на реалізації-заглушці провалилися з `NOT_IMPLEMENTED`; окремий ABA-тест провалився до перевірки inode `current`.
- GREEN: після мінімальних виправлень **8/8** тестів PASS.
- Перевірено на підключеному VPS в ізольованому Node24-контейнері (без мережі, read-only root, без прав Docker усередині): **8/8 PASS**.
- Реальний незмінний реліз `7f886606...` за допомогою нової утиліти: **PASS**, 160 файлів, 103 HTML, точний SHA256 `c05519f...`.
- Повна QA-гілка, executable source `8e1cebac3760d0bda65a46e3bedbe3276fd61f5b`: Node24.22.1, `npm ci`, `npm run check` (0 errors / 0 warnings), **144/144 Vitest**, **16/16 Node** (8 inquiry + 8 artifact), `npm run build` 103 сторінки, `npm run verify:build` PASS, `node --test vps/*.test.mjs` завершився без помилки.
- Збірка QA-гілки в `VSP_PENDING_APPROVAL` дала окремий, **не live**, SHA256 `1c937a71d25c3b6bff8fa7209666191f82c4e2895bb24c1ed521215e3c0ce9bd`. Не підміняти ним контрольний хеш уже розгорнутого релізу.

## Що ще не виконано

- Новий audit script ще **не встановлений** як автоматичний CI/CD gate на VPS. Для автоматичного релізу він має використовувати receipt кожного конкретного білда і бути прив'язаним до release lock; прийняття цієї integration-дії — окремий крок.
- На developer VPS фактично спостерігався новіший реліз `7e774c32863ad6b9f90a95288b5bd3495d941a51`, а відповідний GitHub commit тоді повертав 404. Його source-to-artifact provenance не встановлено, тому нічого не перезаписано.
- Genuine owner enrollment / `readyz` 200, фізичні пристрої, human CAPTCHA, legal/GDPR sign-off, field CWV і офіційне розгортання — не закриті.

Безпечний відкат попередніх окремих тестових релізів залишається незалежним; audit script не містить жодного методу запису/перемикання.
