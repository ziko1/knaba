# Шаблони оформлення KNABA v1

## Межі функції

Модуль додає керування оформленням публічних сторінок у Studio, `/studio/templates/`.
Це каталог трьох довірених пресетів — Original, Business, Modern — і імпорт їхніх параметризованих варіантів. Це не універсальний імпортер сторонніх сайтів. HTML, довільні CSS/JS, assets, WordPress/React/Astro archives, runtime dependencies та installation scripts заборонені. Новий логотип і редактор довільної структури сторінки не входять у формат v1.

Original відновлює наявну розмітку без додаткового CSS. Business/Modern змінюють акценти, поверхні, радіуси, відступи й тіні визначених публічних блоків. Вони не переміщують DOM і не змінюють позиційні селектори редактора Studio. Кабінети, авторизація, форми та маршрути лишаються чинними.

## Для власника

1. Увійдіть як власник та відкрийте Studio → Website-Vorlagen.
2. Виберіть оформлення. Перевірте сторінку однією з шести мов на потрібній ширині.
3. Для власного пакета завантажте приклад, відредагуйте `template.json`, запакуйте ZIP і завантажте його через форму. Перевірка не публікує пакет.
4. Збережіть чернетку. Позначте явне підтвердження та опублікуйте її.
5. Для повернення виберіть попередню публікацію або Original, підтвердьте й натисніть відкат. Нові тексти, клієнти, заявки та повідомлення не відкочуються.

При конфлікті версії оновіть стан, знову перегляньте зміни й підтвердьте публікацію. При невизначеній мережевій помилці «Повторити ту саму дію» надсилає ті самі байти й ключ запиту, щоб не створити повторну публікацію. Після втрати доступу потрібно повторно ввійти.

## Формат ZIP

До 64 KiB архіву й розпакованих даних, максимум два файли у корені: обов'язковий `template.json` і необов'язковий `LICENSE.txt`. Stored/DEFLATE підтримуються. Сервер перевіряє CRC, локальні/центральні заголовки, розмір і співвідношення розпакування, duplicate keys JSON, імена й типи файлів. Зашифровані, вкладені архіви, ZIP64, symlinks, traversal, абсолютні шляхи, extra fields та невідомі файли відхиляються. Не кожен довільний ZIP exporter створює сумісний архів; використовуйте завантажений приклад або `zipfile.ZipFile` без додаткових metadata.

```json
{
  "schemaVersion": 1,
  "id": "my-knaba-design",
  "name": "My KnaBa design",
  "version": "1.0.0",
  "author": "Site owner",
  "license": "Private project use",
  "layout": "business",
  "tokens": {
    "accent": "#174b67",
    "surface": "#f3f7fa",
    "ink": "#143044",
    "radius": 8,
    "density": "compact"
  }
}
```

`id` — lowercase slug 3–64; `name` 1–80, `author` 1–100, `license` 1–120 звичайних символів; `version` — три цілі компоненти; `layout` — original/business/modern. Кольори лише `#RRGGBB`, radius — ціле 0–24, density — comfortable/compact. Невідомі властивості відхиляються. Перевіряється контраст ink/surface та accent/white ≥4.5; це не є повним аудитом доступності всіх сторінок. Завантажувач відповідає за права на оформлення; поле license не є юридичною верифікацією.

SHA-256 рахується з канонічного validated JSON. Вбудовані ID зарезервовані. До 40 незмінних власних пакетів; дубль не витрачає місце. API видалення/експорту всього каталогу v1 не має. Історія зберігається повністю, інтерфейс показує останні 40 публікацій та Original.

## API та захист

Усі маршрути під `/api/studio/templates` вимагають авторизації owner. Мутації використовують чинний same-origin/JSON/custom-header захист порталу. Ідентичність не береться із JSON або заголовків зовнішнього клієнта. VPS заново перевіряє чинну сесію безпосередньо перед записом. Native Worker має працювати лише за довіреним auth ingress.

| Метод і шлях | Контракт |
| --- | --- |
| GET `/` | version, activeDigest, draftDigest, templates, history |
| GET `/example` | Реальний сумісний ZIP для завантаження |
| GET `/preview?digest=…&page=/uk/` | Лише allowlist публічних сторінок; авторизований sandbox preview |
| POST `/upload` | `{ "zip": "base64" }`; не активує оформлення |
| POST `/select` | `{ "digest": "sha256", "version": 0 }` |
| POST `/activate` | `{ "digest": "sha256", "version": 1, "confirm": "PUBLISH", "idempotencyKey": "unique-request-key" }` |
| POST `/rollback` | `{ "revision": 0, "version": 2, "confirm": "ROLLBACK", "idempotencyKey": "another-request-key" }` |

Mutation key 16–100 ASCII літер/цифр/`_`/`-`. Повтор того самого запиту повертає поточний стан; зміна payload під тим самим ключем дає 409. CAS version, active/draft pointer та історія оновлюються транзакційно. До публікації сервер перевіряє рендеринг шести локалізованих home shells. Це не заміняє браузерну перевірку всіх сторінок.

Preview не виконує скрипти та не надсилає форми. HTML очищується, CSP і iframe sandbox обмежують активний контент; assets лише власного origin. Сервер не завантажує довільні URL з пакета. API/preview приватні, no-store/noindex. Public HTML перевіряє active state на кожному запиті; застарілі статичні ETag/304 не приховують нову публікацію. Жодного cache warming/fetch зовнішніх сервісів немає.

## Схема та відновлення

Міграція `0013_site_templates.sql` додає лише `studio_templates`, `studio_template_state`, `studio_template_history` і початковий singleton. Історичні SQL та таблиці не змінюються. Дані окремих workspace ізольовані чинним вибором БД на сервері; client-supplied tenant ID не приймається.

Перед реальним застосуванням зупиніть записи за погодженим планом, створіть перевірену резервну копію та протестуйте її відновлення на іншому файлі/БД. VPS `openLocalDatabase` застосовує міграції лише за чинними правилами запуску; D1 потребує окремої погодженої міграції цільового binding. Команди production у цьому етапі не виконувались.

Відкат оформлення через API безпечний для контенту. Відкат **бінарного релізу** до старої версії — інша операція: старий migration guard відхилить невідому йому 0013. Не запускайте стару версію поверх нової БД. Потрібен заздалегідь перевірений forward fix або погоджене відновлення сумісної резервної копії з урахуванням записів після backup. Не видаляйте migration receipts, щоб обійти guard.

## Перевірки й обмеження

Unit/package, real SQLite API, migration-upgrade, VPS HTTP та production build перевіряються окремими командами. Новий браузерний harness має справжню сесію й тимчасову БД; без браузера він завершується BLOCKED з ненульовим кодом, не PASS. Фактичний звіт додається до checkpoint після завершення перевірок. Device/live/provider acceptance, повний a11y, screenshots та handover readiness залишаються окремими воротами.
