# Website sign-in for the iOS TEST candidate

This adapter uses the accepted first-party F3 server protocol. It does not implement an external identity provider or enable production federation.

## Configuration and user flow

Only a Debug build with both `DEBUG` and `KNABA_FEDERATION_TEST` has the compiled registration `knaba-ios-test-v1` and callback `de.knaba.mobile.ios.test:/auth/federation/callback`. `Info.Debug.plist` adds that one URL scheme; every other source plist value is identical to the existing `Info.plist`. Release uses the unchanged base plist and an empty compiled registry. Bundle identity, minimum iOS 17.0, version/build, signing and location permissions are unchanged.

The user explicitly chooses website sign-in, reviews a configured source and opens `ASWebAuthenticationSession` in the actual window containing the control. The adapter first checks the configured ERP origin's fresh `/api/v1/health` for KNABA DE/apiVersion 1/TEST and its strict federation configuration. Source hostname labels accept the server's 253-character bound. A configured HTTPS source may use its canonical non-default port; this display field does not relax the native app's existing ERP-origin policy or become an arbitrary transport target. System browser cookies are separate from the native ERP client's RAM-only session. An inactive scene while the system browser is shown is not a logout. Entering the background cancels only the unfinished website sign-in and preserves the existing account.

The initial S256 verifier and state are cryptographically generated; a start key is created once. All three are held only in RAM. Start retries require an explicit action and preserve exactly the original key/body. The browser receives only the exact server authorization URL. Completion requires the exact registered callback base plus exactly one code, state and ERP issuer; scheme-only recognition is insufficient. Source password and any existing ERP MFA ceremony run on the server browser surfaces.

## Session boundaries

Token exchange is submitted once, without the old app cookie. Only the exact token endpoint's HTTP 200 response with one new `KF3.<43 base64url>` cookie is a candidate. It must differ from the captured old cookie, be host-only, `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/` and contain bounded valid expiry metadata. Error/redirect/duplicate cookies and old-account `/me` are never recovery evidence.

The typed transport preserves headers when a response body is lost. The user may then explicitly check **only that candidate** via an isolated `/me`, without resending the consumed code. Missing candidate means restart. `/me` does not supply an expiry; the adapter does not fabricate one. Recovery is limited to 120 seconds from receipt headers, capped by validated cookie expiry, any complete token-body expiry and the original server/local attempt deadline. Monotonic uptime also bounds the attempt/recovery, so a wall-clock rollback cannot extend it. These are client limits, not new server session grants.

Both the token profile, when present, and the current candidate profile require TEST mode. With a complete token body, current `/me` must also match its user, company and CSRF. All existing app authority fields, including unknown future scope fields, participate in the original actor revision fence. Same-user role/scope/credential or CSRF changes, logout, local password login, cancellation and origin changes invalidate outstanding work. Network verification returns an opaque VERIFIED candidate with a separate prepared client; it does not switch the active cookie. Only the final synchronous MainActor action retires the old client and installs the new client and UI identity together. Cancellation or backgrounding while that handoff is waiting preserves the old account. Failed/unknown candidate requests do not invoke ordinary login/reset or clear it.

A successful switch permanently invalidates the old client's media/session fence and clears private UI views. Deferred UI actions capture their client, UI revision and origin at the tap; callbacks capture the same client before awaiting, so an old command or logout cannot target the new account. Account-scoped command/media journals remain intact. Candidate preparation and a bounded local metadata check immediately before commit must both succeed. A locked, corrupt or changed recovery journal aborts the switch; a valid pending record remains pending and makes the new account read-only until explicit recovery. There is no await or network between the final deadline/cancellation check and installing the new client and UI. GPS, employee device bearer, background collection and device enrollment remain separate; `LOCAL_ERP_REAUTH_REQUIRED` has explicit localized guidance to use local ERP credentials.

## Verification boundaries

Focused XCTest covers pure protocol/cookie parsing, state/expiry/replay boundaries, a real URLSession with a local URLProtocol stream-failure fixture, client actor races, model adoption/cancellation and the injectable system-browser boundary. These tests are authored here; Linux source checks are not Swift compilation or XCTest execution. The URLProtocol fixture does not contact a server or prove live/native browser behavior.

`scripts/verify-federation-config.py` checks source plist parity. On the existing macOS build path it also inspects both generated build configurations and the actual built Debug plist, then writes a sanitized receipt. Release compilation remains a separate gate. The portable negative tests exercise the checker with explicit synthetic settings; they do not claim that Xcode has resolved those settings locally.

Actual system-browser callback behavior, simulator/device execution of this new adapter, physical device/upgrade/signing/store acceptance and production callback ownership require their own exact-source evidence. The compatible scheme initializer is deprecated in current SDK documentation but remains the baseline for the unchanged iOS 17.0 minimum; no newer API availability is assumed.
