# Адреси сайту та ERP для ботів

Якщо корпоративний сайт і ERP працюють на різних доменах, приватна
конфігурація API/worker має містити дві різні адреси:

```dotenv
PUBLIC_ORIGIN=https://erp.customer.example
BOT_WEBSITE_ORIGIN=https://www.customer.example
```

`PUBLIC_ORIGIN` залишається адресою ERP/API. Telegram webhook налаштовується
на цьому сервері: `https://erp.customer.example/webhooks/telegram`.
`BOT_WEBSITE_ORIGIN` задає сайт, до якого ведуть меню WhatsApp і Telegram:
послуги, контакти та публічні сторінки мовою відвідувача. Без цього розділення
посилання сайту помилково потрапляли б на домен ERP.

`BOT_WEBSITE_ORIGIN` необов’язковий: відсутнє або порожнє значення зберігає
попередню поведінку з `PUBLIC_ORIGIN`. Явне значення має бути кореневою
HTTPS-адресою без логіна, пароля, шляху, query або fragment. Неправильну
адресу відхиляють і `scripts/environment-check.mjs`, і `workerOptions()`;
повідомлення про помилку не повторює значення URL. Дозволена адреса сайту
не замінює обов’язкову HTTPS-перевірку ERP-адреси перед Telegram outbound.

Інсталятор `ops/customer/knaba.py` автоматично встановлює `PUBLIC_ORIGIN`
з `erpDomain`, а `BOT_WEBSITE_ORIGIN` — з `siteDomain`. Ці налаштування
не активують провайдерів: live-прапорці, поточна згода отримувача,
дозволений канал і політика компанії залишаються окремими умовами.
Типова політика `HUMAN_FIRST` не надсилає автоматичного публічного меню;
`RULE_BASED` вимагає явної дозволеної команди керівника з MFA.

Локальні тести конфігурації не виконують запитів до провайдерів.
Синтетичний PostgreSQL-сценарій у `tests/telegram.integration.test.ts`
перевіряє нуль автоматичних відповідей до зміни політики та чинну чергу
після дозволеної тестової зміни; HTTP-адаптер у ньому є явно позначеним
тестовим замінником. Це не доказ реальної доставки Telegram.
