# Encrypted backup and independent restore

PostgreSQL is the authoritative store. `infra/backup.sh` exports a repeatable-read snapshot with exact table counts and SHA256 for both active `media_blobs` and legacy `private_blobs`; private source files can be included explicitly. It encrypts using AES256/PBKDF2 and authenticates the ciphertext with a separately derived HMAC before decryption. The private passphrase must be retained independently under company control. Generated synthetic test keys are never production recovery evidence.

Restore requires `--confirm-empty`, an explicitly named empty database and a distinct source identity. It authenticates ciphertext, verifies archive paths/types, restores atomically, checks the backup's exact original table counts and byte hashes, then requires each media reference to resolve. It subsequently applies the current `infra/001_init.sql` to that destination inside a transaction, runs `knaba_assert_gps_storage_safe()` and purges expired `gps_points` before reporting success. `scripts/restore-drill.mjs` creates a disposable empty database, runs the full restore and cleans up only that new drill database. It never overwrites the source database.

GPS restoration fails closed if legacy raw coordinates remain in `location_sample` aggregates/revisions or `trip.sample` command receipts. The guard does not rewrite immutable historical records. Such a backup needs a separately reviewed migration; disabling the guard or history triggers is not a restore procedure. The purge uses `knaba_purge_gps(now(),500,NULL)` until it returns zero, with at most 1,000 batches and a 60-second purge deadline, per-statement and lock timeouts, and rollback on a failed safety check. It honors current, specific, unexpired GPS legal holds. A failed or bounded-out restore destination must stay isolated from the API and worker; source backups and the original database are untouched.

An encrypted backup can contain raw points until its finite company-approved backup lifespan ends or its recovery key is retired. Encryption alone does not implement deletion. Backup retention, legal holds and key custody/retirement must be agreed for the company, with copies accounted for outside the primary failure domain. Restore removes expired points before access, while retaining the independently governed work-time/payroll facts. These hooks are technical controls, not evidence that a company policy or a live restore drill has been approved or passed.

Integration-test tenants intentionally contain synthetic references. Run restore against a separate clean delivery database with real byte fixtures, not the shared QA database. The latest observed drill on the earlier QA database failed `RESTORED_MEDIA_REFERENCE_MISSING`; the strict reference check is retained. Final local clean-database drill is blocked by socket `EPERM`; it is **NOT PASSED**. The CI workflow contains the reproducible clean-database drill, but its existence does not prove CI executed.

An S3 deployment additionally requires a coordinated encrypted object copy, manifest/version/checksum recovery and a tested private destination. Setting `BACKUP_EXTERNAL_BLOBS_INCLUDED` is an operator assertion, not a successful restore test. Until actual object-backup integration is verified, do not use S3 for production archival. Configure company-approved region, retention, offsite destination, RPO/RTO, custody and incident contacts via the canonical external prerequisite list.
